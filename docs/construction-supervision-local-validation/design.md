# 本地 MaxKB 知识库闭环验收设计

## 1. 节奏

采用“规格 -> 实现 -> 归档”的节奏：

1. 规格：定义验收目标、资料范围、问题集、通过标准。
2. 实现：用脚本校验资料包、配置 MaxKB、上传资料、执行 OCR 后处理与命中验收。
3. 归档：记录本地启动、模型配置、上传结果、OCR 结构化结果、召回质量和下一步改造判断。

## 2. 当前主线

当前最能推进项目、最有价值、也最接近投产的主线，不是继续深挖单个问答效果，而是把真实扫描资料稳定转换成可审查证据。

因此设计主线已经从“本地闭环验收”扩展为：

1. 本地 MaxKB 闭环验收
2. OCR 扫描件接入
3. 证照结构化后处理
4. 精确字段命中验收
5. 前置服务 API 合同草案

一句话：

> 先把扫描件资料变成项目级、队伍级、审查任务级可检索证据，再进入工作流和前端产品化。

## 3. 推荐任务组

### Task Group A：规格收敛

- 确认本地验证目标是知识库闭环，不是生产部署。
- 确认第一批资料包使用 `docx + xlsx`。
- 确认 MaxKB 先使用项目级逻辑知识库。
- 确认扫描件资料必须先走 OCR 派生物和结构化后处理。
- 确认前置平台是事实 owner，MaxKB 只承载支持性检索副本。

### Task Group B：实现验收工具

- 校验 manifest 与实际文件一致。
- 校验必填 metadata。
- 校验 `docx`、`xlsx` 能被 Python Office 库打开。
- 生成上传顺序和审查问题集。
- 支持 OpenAI-compatible 模型配置和资料 API 上传。
- 支持 PaddleOCR-VL 异步 OCR。
- 支持营业执照、安全生产许可证、人员证书结构化后处理。
- 支持项目 / 队伍 / 审查任务元数据写入。
- 支持结构化入库 Markdown 命中验收。

### Task Group C：本地 MaxKB 验收

- 启动 MaxKB。
- 创建项目知识库。
- 上传资料。
- 配置 LLM / Embedding / 可选 Rerank。
- 执行问题集。
- 记录结果。
- 用真实扫描件验证 OCR 入库链路。
- 区分 `keywords` 与 `blend` 两类检索模式的使用场景。

### Task Group D：归档与决策

- 汇总哪些能力现有 MaxKB 已满足。
- 汇总哪些能力需要源码定制。
- 判断下一轮是否进入 metadata 扩展或工作流原型。
- 输出前置服务 OCR 入库 API 合同草案。
- 固化业务元数据标准。

## 4. 验收问题类别

### 开工条件审查

- 资料齐备性
- 队伍资质
- 关键岗位人员
- 特种作业人员
- 机械设备
- 测量试验仪器
- 安全教育和技术交底
- 现场便道和临时排水

### 施工方案审查

- 方案适用范围
- 施工工艺
- 填料来源
- 试验段参数
- 压实与检测
- 质量控制点
- 安全风险控制
- 依据版本

## 5. OCR 资料处理设计

### 5.1 设计原则

- 原始 PDF/图片始终保留，结构化结果不替代原件。
- OCR 原文不直接作为最终入库文本，优先使用结构化 `*-ingest.md`。
- 证照字段检索优先走 `keywords`。
- 审查依据和方案条文检索优先走 `blend`。

### 5.2 当前支持类型

- `business_license`
- `safety_production_license`
- `personnel_certificate`

### 5.3 结构化输出

- `cleaned.md`
- `*-fields.json`
- `*-fields.csv`
- `*-ingest.md`
- `postprocess-report.md`

### 5.4 业务元数据

每份结构化证照建议至少包含：

- `organization_id`
- `project_id`
- `project_name`
- `contract_package_id`
- `team_id`
- `team_name`
- `review_task_id`
- `document_type`
- `source_object_type`
- `source_file_path`

这些字段既进入结构化 JSON，也进入推荐入库 Markdown。

## 6. 决策门槛

只有当本地验证出现以下问题时，才进入源码级改造：

- MaxKB 无法稳定解析 `docx` / `xlsx`
- 无法通过现有知识库配置实现项目 / 队伍 / 审查任务隔离
- 召回结果无法保留足够引用来源
- 工作流无法表达“支持性召回 + 人工确认”的审查模式
- 前置服务无法基于现有脚本稳定封装 OCR / 后处理 / 上传 / 验收接口

否则下一阶段优先做：

1. 真实安全生产许可证回归
2. 真实人员证书回归
3. 前置服务 API 原型
4. 审查工作流原型
