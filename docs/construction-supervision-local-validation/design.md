# 本地 MaxKB 知识库闭环验收设计

## 1. 节奏

采用“规格 -> 实现 -> 归档”的节奏：

1. 规格：定义验收目标、资料范围、问题集、通过标准。
2. 实现：用脚本校验资料包并生成上传计划。
3. 归档：记录本地启动、模型配置、上传结果、召回质量和下一步改造判断。

## 2. 推荐任务组

### Task Group A：规格收敛

- 确认本地验证目标是知识库闭环，不是生产部署。
- 确认第一批资料包使用 `docx + xlsx`。
- 确认 MaxKB 先使用项目级逻辑知识库。

### Task Group B：实现验收工具

- 校验 manifest 与实际文件一致。
- 校验必填 metadata。
- 校验 `docx`、`xlsx` 能被 Python Office 库打开。
- 生成上传顺序和审查问题集。

### Task Group C：本地 MaxKB 验收

- 启动 MaxKB。
- 创建项目知识库。
- 上传资料。
- 配置 LLM / Embedding / 可选 Rerank。
- 执行问题集。
- 记录结果。

### Task Group D：归档与决策

- 汇总哪些能力现有 MaxKB 已满足。
- 汇总哪些能力需要源码定制。
- 判断下一轮是否进入 metadata 扩展或工作流原型。

## 3. 验收问题类别

### 开工条件审查

- 资料齐备性
- 队伍资质
- 关键岗位人员
- 特种作业人员
- 机械设备
- 测量试验仪器
- 安全教育和技术交底
- 现场便道和临时排水

### 施工方案审查

- 方案适用范围
- 施工工艺
- 填料来源
- 试验段参数
- 压实与检测
- 质量控制点
- 安全风险控制
- 依据版本

## 4. 决策门槛

只有当本地验证出现以下问题时，才进入源码级改造：

- MaxKB 无法稳定解析 `docx` / `xlsx`
- 无法通过现有知识库配置实现项目 / 队伍 / 审查任务隔离
- 召回结果无法保留足够引用来源
- 工作流无法表达“支持性召回 + 人工确认”的审查模式

否则下一阶段优先配置和工作流原型，不做后端深改。
