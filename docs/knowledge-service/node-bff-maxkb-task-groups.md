# Node BFF 接 MaxKB 推荐任务组

## 1. 任务组目标

本文件用于把当前建议落成可执行任务组，按“规格 -> 实现 -> 归档”推进。

适用前提：
- 资料审查平台当前已可使用本地/docker 中的 MaxKB 服务
- 本轮不要求立刻切换资料审查平台调用方式
- 本轮优先完善服务端新版本接入能力

## 2. 任务组拆分

### 任务组 A：规格冻结（P0）
目标：把当前阶段边界、接口语义、认证方式、切换顺序定清楚。

输出物：
- `knowledge-service-mvp-spec.md`
- `node-bff-maxkb-implementation-checklist.md`
- 当前文件（任务组）

完成标准：
- 明确“资料审查平台暂不强切”
- 明确“先改 Node BFF/provider，再切消费方”
- 明确 MaxKB 统一使用 `Authorization: Bearer <token>`

### 任务组 B：服务端接入完善（P0）
目标：优先完善 Node BFF 到 MaxKB 的服务端接入，不先改消费端。

建议改动点：
- `knowledgeBaseProvider` 的 MaxKB 路由与配置读取
- Bearer 认证统一拼接逻辑
- 资料审查平台对应的 provider 消费链路
- `reviewIssueSupportingEvidence` 的结果兼容性

完成标准：
- Node BFF 能稳定调用 MaxKB
- 证据与结论链路能返回可消费结构
- 不依赖前端先改造

### 任务组 C：上传与异步入库（P1）
目标：支持材料包、批量文件、大文件场景。

建议改动点：
- 复用现有 `busboy` 上传链路
- MinIO 暂存
- Redis + DB 的 job 管理
- 单文件 split + 批量 batch_create
- 部分成功与粗粒度错误分类

完成标准：
- 大于 20 文件场景不再走同步直返
- 可返回 `job_id`
- 可查询进度与失败文件

### 任务组 D：消费端切换（P1）
目标：在服务端能力稳定后，再切换资料审查平台到新版本。

建议步骤：
1. 保持当前资料审查平台继续可用
2. 在测试环境验证新接口
3. 增加兼容开关或灰度路由
4. 切换到新版本后观察一段时间

完成标准：
- 资料审查平台切换后功能不倒退
- 当前 docker 中的 MaxKB 仍可被服务端稳定调用

### 任务组 E：归档与验收（P0/P1 收口）
目标：把决策、接口、验收结论沉淀下来，避免团队重复讨论。

输出物：
- 决策归档文档
- 联调记录
- 验收结果清单

完成标准：
- 团队知道当前阶段“不改什么”
- 团队知道下一阶段“何时切换”

## 3. 推荐执行顺序

### 第一步：先做 A
先冻结规格和边界，不让执行过程继续发散。

### 第二步：再做 B
先把 Node BFF / provider 与 MaxKB 接稳。

### 第三步：再做 C
需要批量文件与材料包时，再补 job 化。

### 第四步：再做 D
等服务端稳定后，再切换资料审查平台。

### 第五步：最后做 E
把过程沉淀成文档与验收记录。

## 4. 当前阶段的关键判断

如果你现在问“资料审查平台要不要立刻改”：
- 默认答案：不要先改

如果你现在问“当前要先完善哪里”：
- 默认答案：先完善服务端 Node BFF / provider / MaxKB 接入层

如果你现在问“什么时候切消费端”：
- 默认答案：等服务端新版本稳定后再切
