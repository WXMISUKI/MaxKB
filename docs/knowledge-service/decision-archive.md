# Knowledge-Service 决策归档

## 1. 当前阶段决策摘要

### 决策 1：先不重做独立 `/ai/**` 门面
结论：
- 当前第一步不新建独立服务
- 优先复用现有 Node BFF / API Gateway
- 通过 `knowledgeBaseProvider` 接入 MaxKB

原因：
- 仓库里已有 provider 抽象与部分 MaxKB 业务链路
- 当前目标是先用顺，而不是先重构平台边界

### 决策 2：资料审查平台当前可继续使用现有 docker 服务
结论：
- 如果资料审查平台当前可正常使用 docker 中的 MaxKB 服务，则本阶段允许继续使用
- 当前不强制立即切换到新版本服务端接口

原因：
- 先保持业务可用
- 先完善服务端新版本能力，再进行切换

### 决策 3：优先改服务端，不先改消费端
结论：
- 本轮主改动面是 Node BFF、provider、配置、认证、任务编排
- 消费端切换放到下一阶段

### 决策 4：MaxKB 统一使用 Bearer 认证
结论：
- 所有 MaxKB 调用统一使用 `Authorization: Bearer <token>`

原因：
- 这是 MaxKB 当前认证实现的强约束
- 不允许混用其它外部服务的鉴权头格式

### 决策 5：批量文件走异步 job
结论：
- 文件数较多（尤其 >20）时，必须走异步任务
- 使用 MinIO + Redis + DB 进行管理

原因：
- 避免同步超时
- 避免请求体丢失
- 支持部分成功与可观测进度

## 2. 阶段划分归档

### 阶段 0：保持现有可用
- 资料审查平台继续用当前可用链路
- 不打断现有业务

### 阶段 1：完善服务端
- Node BFF + provider + MaxKB 接稳
- 规范 Bearer、环境变量、provider 结果适配

### 阶段 2：切换消费端
- 服务端稳定后，再切资料审查平台/安管平台到新版本

### 阶段 3：平台化演进
- 如果多个产品长期共用，再考虑抽独立 Knowledge-Service 或统一 `/ai/**`

## 3. 当前不建议做的事
- 不建议让前端直连 MaxKB
- 不建议把 MaxKB 当作对外 API 产品暴露
- 不建议在 provider 未稳定前就推动所有消费端切换
- 不建议把 OCR 等其它服务的 header 规则混进 MaxKB 认证链路

## 4. 当前建议做的事
- 先检查并稳定 `knowledgeBaseProvider`
- 先验证 Bearer 认证与 MaxKB 基础连通
- 先打通资料审查平台的证据与结论链路
- 再补上传、异步 job、批量材料包支持
