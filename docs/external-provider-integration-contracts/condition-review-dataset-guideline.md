# 条件审查平台知识库准备规范

本文定义条件审查平台在第一阶段接入 RAGFlow 时，知识库应该准备什么内容、怎么组织、哪些资料不应直接进入库。

## 1. 目标

把知识库内容准备标准化，避免：

- 把不该进库的噪声文件全量导入
- 把过期资料和现行资料混在一起
- 检索结果来源不清
- 后续 stale 判定无据可依

本项目当前优先场景为：

- 某项目下某施工队伍或分包队伍的开工条件审查
- 某项目下某施工队伍或分包队伍的施工方案审查

第一阶段采用“项目级逻辑知识库 + metadata 过滤”的粒度。用户侧看到的是项目知识库，底层必须保留标段、合同段、施工队伍、依据版本、资料类型和审查任务等过滤字段。

详细项目路线见 `../construction-supervision-private-kb-roadmap.md`。

## 2. 第一阶段建议入库的资料类型

优先入库以下内容：

### 2.1 依据类

- 开工条件依据
- 制度办法
- 管理手册
- 业务规则说明
- 审核口径说明

### 2.2 主数据解释类

- 项目主数据口径说明
- 分包队伍分类说明
- 材料字段定义
- 资质字段说明

### 2.3 证据类

- 标准表单
- 代表性已审材料
- 典型样例
- 材料清单说明

### 2.4 经验类

- FAQ
- 典型驳回案例
- 典型通过案例
- 常见错误解释

## 3. 第一阶段不建议直接入库的内容

以下内容不建议第一阶段直接导入：

- 大量重复的原始附件副本
- 未确认版本的草稿
- 仅截图、无文本层、质量极差的扫描件
- 临时沟通记录
- 不可追溯来源的整理稿
- 已失效但未标识版本状态的制度文件

## 4. 推荐文件格式

优先级建议：

1. `docx`
2. `pdf`（可选中文本优先）
3. `md`
4. `txt`
5. `xlsx`

谨慎处理：

- 图片 PDF
- 扫描件
- 压缩包内多层嵌套文件

## 5. 命名规范

建议文件名具备：

- 主题
- 版本
- 生效日期或整理日期

例如：

- `开工条件审核口径_v2026-07-01.docx`
- `分包单位资质要求_现行版_2026-06.pdf`
- `材料清单填写说明_v3.docx`

不建议：

- `最终版.docx`
- `最终版2.docx`
- `最新最新.pdf`

## 6. 推荐 metadata

建议入库时至少保留这些 metadata：

- `organization_id`
- `project_id`
- `contract_package_id`
- `section_id`
- `supervision_section_id`
- `subcontract_team_id`
- `review_task_id`
- `basis_version_id`
- `document_type`
- `source_object_id`
- `content_hash`
- `master_data_ids`
- `evidence_ids`
- `effective_status`
- `effective_date`
- `indexed_at`

其中：

- `project_id` 是第一阶段知识库空间的主要逻辑边界
- `contract_package_id`、`section_id`、`supervision_section_id` 用于标段 / 合同段过滤
- `subcontract_team_id` 用于队伍资料隔离
- `review_task_id` 用于本次审查上传资料的临时范围控制
- `basis_version_id` 用于确保审查使用当前有效依据

## 7. 分批入库建议

第一批建议只放 10 到 30 份高代表性资料，目标是先验证检索质量，不要一开始就全量导入。

推荐顺序：

1. 项目合同依据、招标文件关键条款、项目管理制度
2. 开工条件审查依据和审查表
3. 施工方案审查依据和审查表
4. 一个施工队伍或分包队伍的人员、资质、设备、证照、报审材料
5. 历史典型通过 / 驳回案例

第一批不追求覆盖所有项目资料，而是验证“项目依据 + 队伍资料 + 审查任务资料”能否共同支持一次审查。

## 8. Parser / Chunking 建议

第一阶段可以按资料类型选择：

- 一般制度、说明文档：`naive`
- 法规、条款类：`laws` 或 `manual`
- 问答整理：`qa`
- 表格说明：`table`
- 图片或扫描件：`picture`

如果文档本身结构复杂，优先保证：

- 标题层级清晰
- 正文与附录分开
- 页眉页脚噪声少

## 9. Canonical Storage 原则

平台对象存储（如 MinIO）是正式原始文件存储。

RAGFlow 里的文件副本仅用于：

- 解析
- 分块
- 索引
- 检索

不能把 RAGFlow document id 当作平台原始证据对象的唯一来源。

## 10. Stale 触发条件

以下任一发生后，应考虑重新索引或标记 stale：

- 文件内容变化
- 主数据变化
- 依据版本变化
- provider 侧文档删除
- 分块规则变化
- embedding / rerank 模型切换

## 11. 第一阶段完成标准

知识库准备达到以下状态即可进入联调：

1. 第一批资料主题集中、代表性强
2. 文件名和来源可追溯
3. 至少能区分依据类、主数据解释类、证据类
4. 平台知道何时需要重建索引
5. 检索时可以按项目、标段 / 合同段、施工队伍、依据版本和审查任务过滤
